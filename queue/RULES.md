# Queue Rules

Execution constraints across every wave + phase in `queue/`. Adapted from
[`ymca_ws_canvas_demo/queue/RULES.md`](https://github.com/ITCare-Company/ymca_ws_canvas_demo/blob/feat/standard-pass-w1/queue/RULES.md)
and
[`gogs-cli-queue/RULES.md`](https://github.com/ITCare-Company/template_for_agents/blob/main/process-knowledge-base/gogs-cli-queue/RULES.md).

This queue lives in `yusaopeny_activity_finder` (the ITCare fork). It migrates
**AF4 only** (`openy_af4_vue_app/`). AF3 (`openy_af_vue_app/`) and Camp Finder
(`openy_cf_vue_app/`) are out of scope.

## Dialogue gates

1. **Plan-first.** Before code, post the `## Plan` of the phase in chat. Wait
   for explicit "ok" / "go" / "вйо" before touching any file under
   `openy_af4_vue_app/`.
2. **Verify-first.** After pre-flight green, run the verify snippet (build,
   lint, dev-server smoke, screenshot). Post output / screenshots. Wait for
   "ok" / "push".
3. **Destructive-first.** History rewrite, branch delete, force push,
   `package-lock.json` reset, dependency removal — separate confirmation each
   time. `git status` + `git stash list` first.
4. **Memory-first.** Owner rule ("never X", "always Y") goes into
   [`README.md`](README.md) → "House rules" in the same turn.

## Commit shape

- One phase = one commit. The epic ships via PR (the fork is downstream of
  YCloudYUSA upstream; review required).
- One PR per wave (or one PR for the whole epic if the owner prefers a single
  review surface). Append follow-up commits to the same PR branch — do not
  open a second PR for the same wave (per `feedback_one_pr_per_repo`).
- Subject under 70 characters. Conventional Commits prefix:
  - `docs(queue): …` — queue scaffolding / index / inventory updates
  - `build(af4): …` — build-tool / dependency changes (`package.json`, config)
  - `refactor(af4): …` — Vue 2 → Vue 3 API rewrites with no behaviour change
  - `fix(af4): …` — behaviour-correcting changes surfaced during migration
  - `chore(queue): …` — queue maintenance (≤ one nuance per commit)
- Body explains **why**, references the phase path
  (`see queue/W3-vue3-core-swap/P0-deps-compiler-createapp/`).
- **No** AI-credit trailers (NDA). **No** "Generated with Claude Code"
  footers. **No** `Co-authored-by` lines that disclose tooling.
- Never amend a published commit. Land a new commit.
- Squash merges are forbidden (per `~/.claude/CLAUDE.md`).
- **Never commit a hand-edited `dist/`.** `dist/*.umd.min.js` and
  `dist/*.css` are regenerated by `npm run build` (W7). A `dist/` diff that
  is not the output of a clean build is rejected.

## Pre-flight gates (every phase)

For source changes (W2–W5):

```sh
cd openy_af4_vue_app
npm run lint        # eslint-plugin-vue must pass
npm run build       # UMD lib must build clean (production)
# Then dev-smoke the affected screen (see the phase README "Tests" block).
```

For QA verification (W6):

```sh
# With AF4 mounted on a running Open Y site (or the dev harness from W0-P1),
# capture each affected screen at 1920 / 1024 / 468 and diff against the
# W0 baseline PNGs in queue/W0-baseline-contract/P1-behavioral-baseline/baseline/.
capture-website "<af4 url>" --output <screen>-<vp>.png --full-page --width <vp>
```

For ship (W7):

```sh
cd openy_af4_vue_app && npm ci && npm run build
# Verify the produced UMD exposes the same global + the libraries.yml paths
# still resolve. Then on a Drupal site: ddev drush cr and load the AF4 page.
```

All must be clean before the commit lands.

## Queue maintenance

If a completed phase surfaces a nuance the queue did not anticipate (a
breaking change we missed, a BootstrapVue component with no clean
replacement, a Drupal-side assumption), the **next** commit before further
code work updates the queue:

- Update the affected phase's `## Result` and downstream phases' `## Goal` /
  `## Steps` / `## Out of scope`.
- Update [`INDEX.md`](INDEX.md), [`inventory.tsv`](inventory.tsv), and the
  wave's `DECISIONS.md` — whichever holds the contradicted detail.
- Note the source observation (`see commit <sha>` or `PR #NN`).

`chore(queue): …` commits stay tiny — one nuance per commit.

## Approval gate per phase

Per `feedback_approval_gate_all_fixes`: **no mechanical batch fixes**. Every
phase needs explicit owner approval at three points:

1. Before code lands — `Plan` approved.
2. Before commit — `Verify` output / screenshots approved.
3. Before push to PR branch — diff approved.

## Migration-specific rules

- **Contract before code.** No core swap (W3+) starts until W0-P0 records the
  exact Drupal consumer contract and W0-P1 freezes the visual baseline.
- **Decisions are locked in `DECISIONS.md`.** W1 picks the build tool and the
  BootstrapVue replacement. Once locked, later waves cite the decision; they
  do not re-litigate it mid-stream.
- **De-risk the toolchain separately (W2).** Migrate the build tool while
  still on Vue 2 so a green build proves the toolchain before the framework
  swap mixes in.
- **No behaviour drift.** Each `refactor(af4)` commit must produce identical
  runtime behaviour. Behaviour-correcting changes are `fix(af4)` and need
  their own justification in the phase `## Result`.
- **i18n parity.** `window.Drupal.t`, `Drupal.formatPlural`, and the
  `context: 'Activity Finder'` argument must be preserved exactly when filters
  become methods (W5-P0). A dropped context string is a translation
  regression.
- **Vue runtime delivery is a decision, not a default drop (W1-D4).** Do **not**
  remove `openy_system/vue` / `openy_system/vue-router` from `libraries.yml`
  speculatively. If the build **bundles** Vue 3 (recommended), those deps stay
  inert and `libraries.yml` is untouched; the only work is overriding the
  build's auto-external so `vue` is bundled. `libraries.yml` changes **only** if
  the team chooses to **externalize** to a new `openy_system/vue3` — i.e. when
  there is actually something to externalize. (MIGRATION-REFERENCE §7A.)

## Backend plugin rules (W0b)

- **Default stays Solr.** The extracted Solr backend keeps plugin id `solr` and
  is the block-config default. A block with no stored `backend_plugin` resolves
  to Solr → existing sites stay byte-identical.
- **Use Drupal plugin discovery, not a hand-rolled reader.** Attribute
  `#[ActivityFinderBackend(...)]` + `DefaultPluginManager`. The backend
  *contract* (`OpenyActivityFinderBackendInterface`) is plain PHP and
  CMS-agnostic; only discovery is Drupal's.
- **No new search semantics.** Mock and DB implement the existing interface
  faithfully — same result/facet/pager shape, no invented fields (per
  `feedback_no_fabricated_behavior`).
- **W0b is PHP-only, on Vue 2.** It touches no `openy_af4_vue_app/src` Vue code
  and does not change the consumer contract (block id, library, mount).

## Semantic markup (why automated tests are deferred)

- The current AF4 markup is **non-semantic**: clickable `<div>`/`<span>` with
  `@click` (e.g. `steps/SelectPath.vue`, `FoldableInput.vue`), **zero
  `tabindex`**, uneven `role`/`aria`. Meaningful keyboard / a11y / DOM
  automated tests are **not writable** against it.
- The semantic-markup fix happens **during** the Vue 3 migration (part of the
  per-component rewrite), so **automated tests are future work, after the
  migration** — out of scope for this queue. **QA through W6 is manual (Ira).**
  Do not add a phase promising automated AF4 tests before the markup is fixed.

## Drupal compatibility policy

- **Drupal 11 — required.** Every change (W0b backend plugins, PHP, config,
  `core_version_requirement`) must work on Drupal 11. CI / smoke (W7) run on D11.
- **Drupal 10 — optional (best-effort).** Keep it working where cheap, but D10
  never blocks a D11-correct change. Attribute discovery is native only on
  D10.2+, so the W0b plugin manager keeps an **annotation fallback** only as a
  D10 best-effort (W0b `DECISIONS.md` D9) — not a D11 requirement.
- **Everything else — unsupported.** No D9 or earlier; no PHP versions outside
  the D11 supported range. Do not add compat shims for unsupported cores.
- Current module declares `core_version_requirement: ^10 || ^11`
  (`openy_activity_finder.info.yml`). Treat `^11` as the support target and
  `^10` as best-effort; do not widen the constraint below `^10`.

## Backwards compatibility

- The committed `dist/` for AF3 (`openy_af_vue_app/`) and Camp Finder
  (`openy_cf_vue_app/`) is **untouched** — this queue rebuilds only the AF4
  `dist/`.
- `openy_activity_finder.libraries.yml`, `.module`, `.routing.yml`, and the
  Twig templates under `templates/` are the Drupal-side consumer. They change
  **only** if W7 proves a contract shift is unavoidable — and then with an
  explicit `DECISIONS.md` entry.
